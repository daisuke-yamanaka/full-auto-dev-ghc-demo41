# 方式設計書

## 1. システム概要

### 1.1 アーキテクチャ概要
（パターンB採用: ドロワーメニュー型 + Material Designインスパイア）

本システムはSpring Boot（バックエンド）とReact（フロントエンド）による SPA + REST API 構成を採用する。バックエンドは以下の4層レイヤー構造とする。

```
[クライアント（React SPA）]
        ↓ HTTP/JSON
[Controller層] ← リクエスト受付・レスポンス整形・入力バリデーション
        ↓
[Service層]    ← ビジネスロジック・トランザクション制御
        ↓
[Repository層] ← データアクセス（Doma3）
        ↓
[データベース（H2/PostgreSQL）]
```

### 1.2 技術スタック

| レイヤー | 技術 | バージョン（目安） |
|---------|------|----------------|
| フロントエンド | React | 18.x |
| フロントエンド | TypeScript | 5.x |
| フロントエンド | Axios | 1.x |
| フロントエンド | React Router | 6.x |
| バックエンド | Spring Boot | 3.x |
| バックエンド | Spring Security | 6.x |

## 2. トランザクション方針

- Service層のメソッドに `@Transactional` アノテーションを付与してトランザクション管理を行う。
- 読み取り専用処理（GET系）には `@Transactional(readOnly = true)` を付与し、パフォーマンスを最適化する。
- 更新・削除・登録処理には `@Transactional` を付与し、失敗時はロールバックする。
- Service層から呼び出す複数のRepositoryメソッドは同一トランザクション内で実行されることを保証する。
- トランザクションの伝播は基本的に `REQUIRED`（デフォルト）を使用する。

```java
// 例：読み取り専用サービス
@Transactional(readOnly = true)
public List<BookDto> searchBooks(BookSearchCondition condition) { ... }

// 例：更新系サービス
@Transactional
public LoanResponse createLoan(Long userId, Long bookId) { ... }
```

## 4. 認証・セッション設計

### 4.1 JWT認証フロー

```
1. クライアントが POST /api/auth/login にユーザIDとパスワードを送信
2. サーバが認証情報を検証し、JWTトークンを生成して返却
3. クライアントは以降のリクエストで Authorization: Bearer <token> ヘッダを付与
4. サーバは JwtAuthenticationFilter でトークンを検証し、ユーザ情報をSecurityContextに設定
```

### 4.2 JWTトークン仕様

| 項目 | 内容 |
|------|------|
| アルゴリズム | HS256 |
| 有効期限 | 30分（1800秒） |
| クレーム（payload） | sub（userId）, role, iat, exp |

### 4.3 多重ログイン防止（シングルセッション制御）

トークンブラックリスト方式を採用する。

| 項目 | 内容 |
|------|------|
| 方式 | DBの `user_sessions` テーブルで有効なトークンを管理 |
| ログイン時 | 既存のセッションレコードを削除（または無効化）し、新しいトークンを登録 |
| ログアウト時 | セッションレコードを削除し、トークンを無効化 |
| リクエスト時 | JwtAuthenticationFilter でトークンがDBに存在することを確認 |
| タイムアウト処理 | 有効期限切れトークンのセッションは定期バッチまたはアクセス時に削除 |

**user_sessions テーブル構造**

```sql
CREATE TABLE user_sessions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    token_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_sessions_user FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX idx_user_sessions_token_hash ON user_sessions (token_hash);
CREATE INDEX idx_user_sessions_user_id ON user_sessions (user_id);
```

## 5. 排他制御方針（楽観的ロック）

### 5.1 概要

楽観的排他制御をアプリケーションレベルで実装する。競合が発生する可能性のある全テーブルにバージョンカラムを設け、更新時にバージョンの一致を確認する。

### 5.2 対象テーブル

| テーブル | バージョンカラム | 理由 |
|---------|--------------|------|
| users | version | プロフィール更新の競合防止 |
| books | version | 図書情報更新・削除の競合防止 |
| loans | version | 返却処理の競合防止 |
| reservations | version | 予約キャンセルの競合防止 |

### 5.3 楽観的ロック処理フロー

```
1. クライアントはリソース取得時に version 値を受け取る
2. 更新リクエスト時に version 値をリクエストボディに含めて送信
3. Service層でSELECT → バージョン確認 → UPDATE/DELETE
4. DBのversionが受信したversionと一致する場合のみ更新を実行
5. 一致しない場合は OptimisticLockException をスロー → HTTP 409 Conflict を返却
```

```java
// Repository実装例
public int updateBook(Book book) {
    String sql = "UPDATE books SET title=:title, ..., version=version+1, updated_at=CURRENT_TIMESTAMP "
               + "WHERE id=:id AND version=:version";
    int affected = jdbcTemplate.update(sql, params);
    if (affected == 0) {
        throw new OptimisticLockException("Book was updated by another transaction");
    }
    return affected;
}
```

### 5.4 エラーレスポンス

- HTTP 409 Conflict
- エラーコード：`OPTIMISTIC_LOCK_ERROR`
- メッセージ：「他の端末から変更が行われました。再読み込みしてください。」

## 6. 操作ログ設計

### 6.1 概要

主要な操作（貸出・返却・予約・キャンセル・登録・更新・削除・ログイン・ログアウト）をデータベースの `operation_logs` テーブルに記録する。

### 6.2 ログ記録方式

**方式1: AOP（@Around）によるServiceメソッドの自動ログ記録**

```java
@Aspect
@Component
public class OperationLogAspect {
    @Around("@annotation(operationLog)")
    public Object logOperation(ProceedingJoinPoint joinPoint, OperationLog operationLog) {
        // OperationLogService.record() を呼び出してログを記録
    }
}
```

**方式2: OncePerRequestFilter によるHTTPリクエストログ**

```java
@Component
public class HttpRequestLogFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, ...) {
        // リクエストメソッド、URL、IPアドレス、ユーザIDをログに記録
    }
}
```

### 6.3 ログ対象操作

| 操作種別 | トリガー | ターゲット種別 |

## 7. エラーハンドリング方針

### 7.1 GlobalExceptionHandler

`@RestControllerAdvice` を使用した一元的な例外ハンドリングを実装する。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class) // → 400
    @ExceptionHandler(ConstraintViolationException.class)   // → 400
    @ExceptionHandler(AuthenticationException.class)         // → 401
    @ExceptionHandler(AccessDeniedException.class)           // → 403
    @ExceptionHandler(ResourceNotFoundException.class)       // → 404
    @ExceptionHandler(OptimisticLockException.class)         // → 409
    @ExceptionHandler(Exception.class)                       // → 500
}
```

### 7.2 HTTPステータスコードマッピング

| 例外クラス | HTTPステータス | エラーコード | 説明 |
|-----------|--------------|-------------|------|
| MethodArgumentNotValidException | 400 Bad Request | VALIDATION_ERROR | 入力バリデーションエラー |
| ConstraintViolationException | 400 Bad Request | VALIDATION_ERROR | 制約違反 |
| BadCredentialsException | 401 Unauthorized | AUTHENTICATION_ERROR | 認証失敗 |
| JwtException | 401 Unauthorized | TOKEN_INVALID | JWTトークン無効 |
| AccessDeniedException | 403 Forbidden | FORBIDDEN | 権限不足 |
| ResourceNotFoundException | 404 Not Found | NOT_FOUND | リソース未存在 |
| OptimisticLockException | 409 Conflict | OPTIMISTIC_LOCK_ERROR | 楽観的ロックエラー |
| BusinessLogicException | 409 Conflict | BUSINESS_LOGIC_ERROR | ビジネスロジックエラー（貸出上限・延滞等） |
| Exception | 500 Internal Server Error | INTERNAL_SERVER_ERROR | 予期しないエラー |

### 7.3 エラーレスポンス形式

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容に誤りがあります",
  "details": [
    "タイトルは必須です",
    "ISBNは10桁または13桁の数字で入力してください"
  ]
}
```

## 8. フロントエンド設計方針

### 8.1 採用デザインパターン

**パターンB：ドロワーメニュー型 ＋ Material Designインスパイア**

| 項目 | 内容 |
|------|------|
| ナビゲーション | ハンバーガーアイコン起動のドロワーメニュー（オーバーレイ）。PCではピン留めで常時表示に切り替え可能 |
| ログイン後の遷移先 | アクティビティフィード画面（最新の貸出・返却・予約をタイムライン表示） |
| 配色 | 背景 `#ffffff`/`#f8f9fa`、プライマリ `#1a73e8`（Googleブルー）、アクセント `#00897b`（ティール） |
| カードUI | カード型UIで情報をグループ化、シャドウ＋余白で階層を表現 |
| 通知 | バッジ＋スナックバー（下部）で非侵入的に表示 |
| レスポンシブ | PC(≥1024px)・タブレット・スマホ全対応 |
| localStorage | ドロワーのピン留め状態は `localStorage` で維持 |

### 8.2 状態管理

| 状態 | 管理方式 |
|------|---------|
| 認証情報（JWTトークン、ユーザ情報） | React Context + localStorage |
| フォントサイズ設定 | React Context + localStorage + サーバ（DB） |
| ドロワーのピン留め状態 | localStorage |
| 画面ごとのデータ | React useState / useEffect |

### 8.3 APIクライアント設計

- Axiosのインスタンスを作成し、baseURL・タイムアウトを設定
- リクエストインターセプタで Authorization ヘッダを自動付与
- レスポンスインターセプタで 401 Unauthorized を検知し、自動ログアウト処理を実行
