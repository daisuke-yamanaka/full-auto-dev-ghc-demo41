# 設計工程 rules

## 工程開始チェック
- 要件定義書、モックが全て揃っていない場合、作業を中断して。

## 設計工程（モック承認後に実施）

### 要件定義書とモックから設計書へ反映（必須）
- 方式設計
  - アーキテクチャ設計
  - 技術スタック
  - レイヤー構成
  - トランザクション方針
  - セキュリティ設計
  - 認証・セッション設計
  - 排他制御方針
    - 排他制御（楽観的ロック）では、並行競合が発生し得る全テーブル（ステータスが更新されるテーブルを含む）を対象テーブルリストに含め、各テーブルのDDLにバージョン管理用カラムを定義して。
  - 操作ログ設計
  - エラーハンドリング方針
- API仕様書
- データ設計
  - ER図
  - DDL
- 入力仕様
  - 入力項目定義
  - バリデーションルール
- 操作設計
  - 画面一覧（画面ID、画面名、モックのファイル名、概要）
  - 操作シナリオ
  - **画面設計書（SCR*.md）の必須定義項目**
    各画面の設計書には以下を必ず含めること：
    - **ボタン表示条件表**：ログインユーザーの状態（未処理・処理中・完了・上限到達等、対象システムの状態に応じた状態名）を行に、画面上の全ボタンを列に取り、「表示（活性）」「表示（非活性）」「非表示」の3値で全組み合わせを網羅すること
    - **アクション定義（A01〜AN）の網羅**：「〇〇リンク押下 → SCR00X へ遷移」形式のナビゲーションアクションも必ず A0N として定義し、対応する API エンドポイントを関連 API 表に記載すること
    - **B・A・API の3層整合**：画面項目定義のボタン（B0N）→ アクション定義（A0N）→ 関連 API の対応関係に漏れがないこと
    - **承認済みモックとの対応**：対応する承認済みモックのファイルパス（例：`docs/mockup/pattern-b/scr001.html`）を記載し、以下のデザイン仕様を転記すること
      - 採用パターン名（A/B/C）とナビゲーション構造（サイドバー・アイコンナビ・タイルホーム等）
      - 配色仕様（背景色・プライマリカラー・アクセントカラー・テキスト色）
      - コンポーネントスタイル（カード・ボタン・フォーム・テーブル等の視覚仕様）
      - 空状態・ローディング・エラー状態の表示仕様（メッセージ文言・レイアウト）
      - **これらが設計書に記載されていない場合、設計レビューはNG**
- フロー設計
  - アクティビティ図
  - ユースケース図

### API仕様の確定
- 設計工程において、フロントエンドとバックエンドが共有するAPI仕様を確定して。
- API仕様は `docs/design/openapi.yaml`（OpenAPI 3.0形式）として作成し、設計のフィーチャーブランチにコミットして。
- 各APIエンドポイントには以下を必ず定義して：
  - **HTTPメソッドとURL**：URLには「誰が・何を対象に操作するか」の意図を明示すること（例：認証ユーザ自身のデータを取得する場合は `/api/me/...`、管理者が全ユーザのデータを操作する場合は `/api/admin/...` のようにURLで役割を区別する）
  - **パスパラメータ・クエリパラメータ**：型・必須任意・説明を明記
  - **リクエストボディ**：フィールド名・型・必須任意・バリデーション制約
  - **レスポンス**：各HTTPステータスコード（200/201/400/401/403/404/409/500）に対するレスポンスのJSONスキーマ
  - **認証・認可要件**：エンドポイントにアクセス可能なロール（未認証可/一般ユーザ/管理者等）を明示
- URLの命名は説明文だけで意図を伝えるのではなく、**URLパス自体に操作の意図・対象ロールを反映**させること。命名の曖昧さがフロント・バック間で独自解釈を生む根本原因となるため、以下の原則に従うこと：
  - 認証ユーザ自身のリソース：`/api/me/resource`（例：`GET /api/me/profile`、`GET /api/me/orders`）
  - 管理者専用操作：`/api/admin/resource`（例：`GET /api/admin/users`、`DELETE /api/admin/users/{id}`）
- エラーレスポンス専用セクションを設け、各HTTPステータスコード（400/401/403/404/409/500）に対応するレスポンスのJSONスキーマ（フィールド定義）を記述して。
- **レスポンスフィールドの網羅確認（必須）**
  以下の3種類のフィールドが各レスポンスに不足していないか、画面設計書（SCR*.md）と突合して確認すること：

  1. **楽観的ロック用 `version` の網羅**
     - フロントエンドから更新・削除操作が発生するリソースを含むすべてのレスポンス（一覧・詳細・集約レスポンス等）に `version` フィールドを定義すること
     - 集約レスポンス（ダッシュボード等）内に操作ボタンを表示する場合、操作対象エンティティの `version` を必ず含めること

  2. **ユーザー状態判定用フィールドの網羅**
     - ログインユーザーの状態によって UI が変わる画面のレスポンスには、画面状態遷移表（SCR*.md）の各状態を判定するために必要なフィールドをすべて定義すること
     - 典型的な例：操作対象リソースの所有・処理中フラグ（`currentUserResourceId` 等）、楽観的ロック用バージョン（`currentUserResourceVersion` 等）、申請・処理状態（`currentUserStatus` 等）。フィールド名は対象システムのドメインに合わせること

  3. **ナビゲーション用 ID の網羅**
     - 一覧・集約画面のレスポンスで、リソース名等クリック時に詳細画面へ遷移する要素があれば、遷移先を特定するリソース ID を必ず含めること
     - 画面設計書のアクション定義（「〇〇リンク押下 → SCR00X へ遷移」）を参照し、ナビゲーション元の全レスポンスに ID が含まれていることを確認すること

## レビュー方針

- レビューの結果で品質がOKになるまで、次の工程を実行しないで。
- レビューでは別の新たなサブエージェントを使い、役割を分担してレビューして。
- レビューエージェントはgit worktreeで独立した作業ディレクトリを使用して。
- レビュー指摘が誤っていないか、指摘対象のコードを確認して、ファクトチェックして。
- レビュー指摘が重複していたら取り除いて。
- レビュー指摘が誤っていたら、指摘を取り下げて。
- レビュー指摘を修正したら、次の工程に進まないで、再レビューを実施し、修正すべき指摘がなくなるまで、レビューを繰り返して。
- 再レビューでは別の新たなサブエージェントを使い、レビューの役割を分担して。
- 重要な指摘だけでなく、必ず軽微な指摘でも処置して。
- レビュー結果はPRのdescriptionに以下の形式で記載して。
  ```
  ## レビュー結果
  | 指摘番号 | 重要度 | 指摘内容 | 対応結果 |
  |---------|--------|---------|---------|
  | R-001   | 重要   | ...     | 修正済み |
  ```
- レビュー完了後、フィーチャーブランチからPRを作成して。
- 設計では要件定義の充足確認に加えて、モックとの整合性を検査して。
- API仕様のレビューでは、フロントエンドとバックエンドの両視点から以下を確認して：
  - URLの命名がロール・対象リソース・操作意図を明示しているか
  - 全機能要件（FR-xxx）に対応するエンドポイントが網羅されているか
  - レスポンス形式がフロントエンドの表示要件を満たせるか（必要なフィールドが含まれているか）
  - 楽観的ロックが必要な全リソースのレスポンスに `version` が定義されているか
  - 画面状態遷移表の全状態を判定するために必要なユーザー状態判定フィールド（`currentUser*` 等）が定義されているか
  - 各画面設計書の全アクション定義（A01〜AN）に対応する API が定義されているか
  - ナビゲーション元レスポンスに遷移先リソース ID が含まれているか
  - **上記のいずれかが未達成の場合、設計レビューはNG**
- 画面設計書（SCR*.md）のレビューでは以下を確認して：
  - ボタン表示条件表がユーザーの全状態 × 全ボタンの組み合わせを網羅しているか
  - ボタン（B0N）・アクション（A0N）・関連 API の3層が漏れなく対応しているか
  - ナビゲーションアクション（「〇〇リンク押下 → SCR00X へ遷移」）が A0N として定義されているか
  - **上記のいずれかが未達成の場合、設計レビューはNG**

## ドキュメント品質基準

### 用語の統一
- 要件定義書の用語集に定義した表記を一貫して使用して（例：「ユーザ」と「ユーザー」の混在は不可）。

### ドキュメント間の整合性
- ドキュメント間で矛盾が発生した場合は、矛盾を解消してから次工程へ進んで。

### 表記規則
- 権限マトリクスや一覧表の「可/否」を示す記号は「○」（丸記号）を使用して。アルファベットの「O」はゼロ「0」と混同するため使用しないで。
- 実装者が一意に解釈できるよう、曖昧な表現を避けて。

## GitHubワークフロー方針

- issueは使用しません。
- ブランチ戦略は以下の通りとする。
  - `main`ブランチ：リリース可能な状態を維持する保護ブランチ
  - `develop`ブランチ：各工程のPRをマージする統合ブランチ
  - 工程別フィーチャーブランチ：`feature/<工程名>`の命名規則で作成（例：`feature/requirements`、`feature/mockup`、`feature/design`、`feature/implementation`、`feature/unit-test`、`feature/e2e-test`）
- 各工程の作業開始時に、`develop`ブランチから対応する`feature/<工程名>`ブランチを作成して。
- 各工程の作業終了時に、`develop`ブランチへマージして。
- 各工程の成果物（mdファイル・コード等）は必ずフィーチャーブランチにコミットして。
- レビューが完了したら、`feature/<工程名>`ブランチから`develop`ブランチへのPRを`gh pr create`で作成して。
- PRの説明には、工程名・主な成果物・レビュー結果サマリを記載して。
- PRのマージは`gh pr merge --squash`で行い、フィーチャーブランチは削除して。
- 全工程完了後、`develop`から`main`へのPRを作成してマージして。
- git worktreeを活用して、複数のサブエージェントが並行して異なるブランチで作業できるようにして。
  - worktreeの作成：`git worktree add <path> <branch>`
  - worktreeの削除：`git worktree remove <path>`
  - レビューエージェントは専用のworktreeで独立して作業して。
