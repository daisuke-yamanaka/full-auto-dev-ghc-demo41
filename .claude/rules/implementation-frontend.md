# 実装（フロントエンド）工程 rules

## 工程開始チェック
- 要件定義書、モック、設計書、実装（バックエンド）が全て揃っていない場合、作業を中断して。

## 実装方針
- 実装はgit worktreeを使って、複数のサブエージェントが並行して異なるモジュールを実装して。ただし、バックエンドとフロントエンドの並行実装は禁止する。バックエンドAPIの実装・動作確認を完了してからフロントエンドの実装を開始すること。バックエンド内の複数モジュール間、またはフロントエンド内の複数モジュール間の並行実装は可。
- コミットメッセージは「[工程名] 作業内容の概要」の形式で統一して（例：`[impl] ユーザ認証機能を実装`）。
- 各工程の完了時に必ずPRを作成し、PRのCIチェック（テスト・ビルド）をパスしてからマージして。
- レビューによってコード修正した場合、関連する設計書を修正すること。ただし、ヒアリングシートと要件定義書の変更は禁止。

### 承認済みモックのデザイン再現（必須）
- フロントエンド実装は、承認済みモック（`docs/mockup/採用パターン/`）を**必ず参照**し、以下のビジュアル仕様を忠実に再現すること。
  - **ナビゲーション構造**：サイドバー・アイコンナビ・タイルホーム等、採用パターンのナビゲーション構造をそのまま実装すること
  - **配色**：モックで使用した背景色・プライマリカラー・アクセントカラーを CSS 変数または定数として定義し、モックと同一の色を適用すること
  - **コンポーネントスタイル**：カード・ボタン・フォーム・テーブル等の外観（角丸・シャドウ・余白・フォントサイズ）をモックに合わせること
  - **空状態・エラー状態の表示**：モックに定義された空状態メッセージ・エラーメッセージの文言・レイアウトを再現すること
- 採用パターンは設計書の画面設計書（SCR*.md）に記載された「承認済みモックとの対応」セクションで確認すること。
- モックと実装の外観が著しく異なる場合、実装レビューはNG。

### API仕様の実装遵守（必須）
- バックエンド・フロントエンドの実装時は、設計で確定した `docs/design/openapi.yaml`（OpenAPI仕様書）を必ず参照し、APIの契約として厳格に遵守すること。
- エンドポイントURL・HTTPメソッド・パスパラメータ・クエリパラメータ・リクエストボディのフィールド名と型・レスポンスのJSON構造は、すべて openapi.yaml の定義に正確に従うこと。独自解釈による実装を禁止する。
- openapi.yaml に定義されていないAPIエンドポイントを独自に追加してはいけない。追加が必要な場合は、まず openapi.yaml を更新し、バックエンド・フロントエンド双方の実装に反映すること。
- フロントエンドのAPI呼び出し（URL・HTTPメソッド・リクエスト/レスポンスの型定義）は、openapi.yaml から生成またはopenapi.yamlを見ながら実装し、ハードコーディングによる齟齬を防ぐこと。

- 各機能を実装するたびに、スキル「/simplify」とスキル「/eslint」を実行して、指摘事項を修正してから、実装レビューを行って。

### ログ実装（必須）
- 使用言語・フレームワークの標準的なロギング機構を利用して。
- 以下の操作は必ず INFO レベルで操作ログを出力して。
  - ログイン成功・失敗
  - 主要なビジネス操作（登録・更新・削除・ステータス変更等）
  - ユーザ・リソースの登録・更新・削除（管理者操作を含む）
- **操作ログには必ず「操作者のユーザID」を含めて。** ビジネスロジック層でも認証情報から操作者IDを取得してログに含めること。
- 例外キャッチ箇所では必ずスタックトレース付きで ERROR レベルのログを出力して。
- ログレベルの設定を設定ファイルに明記して。

### 例外処理（必須）
- グローバル例外ハンドラーを必ず実装して。
- カスタム例外のハンドリングは各コントローラーに散在させず、グローバルハンドラーに集約して。
- DB制約違反はフレームワーク固有の例外クラスでキャッチして。汎用の例外クラスをキャッチしてエラーメッセージの文字列マッチで判定することを禁止します。

### DRY原則の徹底
- 同一ロジックの重複を排除し、共通処理はヘルパーメソッドやユーティリティクラスに抽出して。
- 特に以下のパターンは必ず共通化すること：
  - 同一のUI表示ロジックが複数コンポーネントに存在する場合は共通コンポーネントとして抽出すること
  - API呼び出しロジックが複数箇所に存在する場合は共通のAPIクライアント/フックに集約すること
- **同一ロジックが3箇所以上に重複している場合、実装レビューはNG**

### 定数管理
- ビジネスルールの数値（各種上限値・期限日数等）をマジックナンバーとして直接コードに記述することを禁止します。定数または設定値として定義して。

### セキュリティ実装（必須）
- CSRFトークンをログインページを含む全ページに設定して。Ajax通信でもCSRFトークンが送信されるようにして。
- 本番環境の設定ファイルで、DB接続パスワード等の機密情報にデフォルト値（空文字を含む）を設定することを禁止します。環境変数が未設定の場合はアプリ起動が失敗する設定にして。

### 環境設定管理（必須）
- 設定ファイルを単一ファイルのみで管理することを禁止します。環境ごとに設定ファイルを分離して。
  - 共通設定ファイル：全環境共通の設定のみ
  - 開発環境専用設定ファイル：DBコンソール有効化、デバッグログ等の開発専用設定
  - 本番環境専用設定ファイル：本番DB設定、INFOログ、DBコンソール無効等
- 開発専用の機能は必ず開発環境の設定にのみ記載し、共通設定や本番設定に含めないで。
- 環境切り替えは環境変数で制御できるようにし、設定ファイルの手動書き換えは不可とする。

### Reactフロントエンドテスト品質（必須）
- テストフレームワークは **Jest + React Testing Library** を使用してください。
- **全ページコンポーネント**（`src/pages/` 配下等）に対してテストファイルを作成してください。選別せず全ページを対象とすること。
- **共通コンポーネント**（`src/components/` 配下等）のうち、条件分岐・状態変化・ユーザー操作を含むものは必ずテストを作成してください。
- **カスタムフック**（`src/hooks/` 配下等）は全て `renderHook` を使用してテストを作成してください。
- **API通信（Axios）のテスト**は `axios` をモック化（`jest.mock('axios')`）してテストしてください。実際のHTTPリクエストをテスト内で発行することを禁止します。
- フォームの入力・送信・バリデーションエラー表示は `userEvent` を使用してユーザー操作をシミュレートしてテストしてください。
- 非同期処理（API呼び出し後の画面更新等）のテストには `waitFor` または `findBy*` クエリを使用してください。
- `getByTestId` への過度な依存を避け、`getByRole`・`getByLabelText`・`getByText` 等のアクセシビリティベースのクエリを優先してください。
- Reactフロントエンドのテストカバレッジは **90%以上** を目標としてください。カバレッジが低い場合はページコンポーネントとカスタムフックを優先して補強してください。

## レビュー方針（実装）
- レビュー指摘は後で人間が確認するので、記録として残して。
- レビューの結果で品質がOKになるまで、次の工程を実行しないで。
- レビューでは別の新たなサブエージェントを使い、役割を分担してレビューして。
- レビューエージェントはgit worktreeで独立した作業ディレクトリを使用して。
- レビュー指摘が誤っていないか、指摘対象のコードを確認して、ファクトチェックして。
- レビュー指摘が重複していたら取り除いて。
- レビュー指摘が誤っていたら、指摘を取り下げて。
- レビュー指摘を修正したら、次の工程に進まないで、再レビューを実施し、修正すべき指摘がなくなるまで、レビューを繰り返して。
- 再レビューでは別の新たなサブエージェントを使い、レビューの役割を分担して。
- 重要な指摘だけでなく、必ず軽微な指摘でも処置して。
- レビュー結果はPRのdescriptionに以下の形式で記載して。mdファイルへの別途記録は不要です。
  ```
  ## レビュー結果
  | 指摘番号 | 重要度 | 指摘内容 | 対応結果 |
  |---------|--------|---------|---------|
  | R-001   | 重要   | ...     | 修正済み |
  ```
- レビュー完了後、フィーチャーブランチからPRを作成して。
- 実装レビューでは設計書との整合性を必ず確認して。特に以下の点を検査すること：
  - テンプレート/ビューのフォルダ名・エンドポイントパス（パスプレフィックス含む）が設計書と一致していること
  - クラス/モジュールの依存関係が設計書と一致していること
  - データ転送オブジェクト（DTO等）のフィールド構成が設計書と一致していること
  - 差異がある場合は設計書を実装に合わせて更新すること（ヒアリングシートと要件定義書は除く）
- 実装レビューでは `docs/design/openapi.yaml` との整合性を必ず確認して。特に以下の点を検査すること：
  - フロントエンドのAPI呼び出し先URL・HTTPメソッド・リクエスト/レスポンスの型定義が openapi.yaml と一致していること
  - パスパラメータ・クエリパラメータの名前と型が openapi.yaml と一致していること
  - **上記のいずれかが未達成の場合、実装レビューはNG**

## 完了前必須チェックリスト（実装工程）

### ログ実装の確認
- 全サービスクラス（ビジネスロジック層）にロガーが定義されていること
- ログイン成功・失敗のログが存在すること
- 主要なビジネス操作（登録・更新・削除・ステータス変更等）に INFO ログが存在すること
- 例外キャッチ箇所にスタックトレース付き ERROR ログが存在すること
- **上記が一つでも未達成の場合、実装レビューはNG（このチェックをスキップしてはいけません）**

### グローバル例外ハンドラーの確認
- グローバル例外ハンドラーが実装されていること
- カスタム例外のハンドリングが各コンポーネントに散在せず、グローバルハンドラーに集約されていること
- **未実装の場合、実装レビューはNG**

### 環境設定分離の確認
- 開発環境専用設定ファイルが存在すること
- 本番環境専用設定ファイルが存在すること
- 開発専用機能の設定が共通設定・本番設定ファイルに含まれていないこと
- **未実装の場合、実装レビューはNG**

### 定数管理の確認
- ビジネスルールの数値（各種上限値・期限日数等）が定数または設定値として定義されていること
- マジックナンバーとしてコードに直接記述されていないこと
- **マジックナンバーが発見された場合、実装レビューはNG**

### API仕様整合性の確認
- フロントエンドの全API呼び出し（URL・HTTPメソッド・リクエスト/レスポンスの型定義）が `docs/design/openapi.yaml` と一致していること
- openapi.yaml に定義されていない独自エンドポイントが追加されていないこと
- **上記が一つでも未達成の場合、実装レビューはNG（このチェックをスキップしてはいけません）**

### 画面設計書アクション定義の網羅確認
`docs/design/screens/SCR*.md` の各画面について以下を1件ずつ突合すること：

- **全アクション定義（SCR00X-A01〜A0N）が実装されていること**
  - 特に「〇〇リンク押下 → SCR00X へ遷移」形式のナビゲーションアクションは見落としやすいため重点確認
  - 未実装のアクションが1件でもあれば実装完了を宣言してはいけない
- **画面状態遷移表の全状態が実装されていること**
  - ユーザーの現在の状態（対象システムの状態名に応じて、例：未処理/処理中/承認済み/却下 等）に基づくボタン表示の分岐は、全状態のボタン表示・非表示・ラベルを確認すること
- **同一 UI パターンの横展開確認**
  - 「リソース名クリックで詳細へ遷移」「ステータス変更ボタン」など同じ UI パターンが複数画面に存在する場合、全画面に実装されていることを一括確認すること
- **上記が一つでも未達成の場合、実装レビューはNG**

### Reactフロントエンドテストの確認
```bash
find frontend/src -name "*.test.tsx" -o -name "*.test.ts" -o -name "*.spec.tsx" -o -name "*.spec.ts" 2>/dev/null | sort
```
- 全ページコンポーネントに対応するテストファイルが存在すること
- **テストファイルが存在しないページコンポーネントが発見された場合、テストレビューはNG**

```bash
grep -rn "jest.mock.*axios\|axios.*mock" frontend/src/ --include="*.test.*" --include="*.spec.*" 2>/dev/null
```
- API通信を含むテストで `axios` がモック化されていること
- **実際のHTTPリクエストを発行しているテストが発見された場合、テストレビューはNG**

```bash
grep -rn "getByTestId" frontend/src/ --include="*.test.*" --include="*.spec.*" 2>/dev/null
```
- `getByTestId` を多用していないこと（`getByRole`・`getByLabelText`・`getByText` を優先すること）
- **`getByTestId` が大部分のクエリに使用されている場合、テストレビューはNG**

Reactテストカバレッジの確認：
```bash
cd frontend && npx jest --coverage --coverageReporters=text-summary 2>/dev/null | tail -5
```
- テストカバレッジが **90%以上** であること
- **90%未満の場合、テストレビューはNG（ページコンポーネント・カスタムフックを優先して補強すること）**

## GitHubワークフロー方針
- issueは使用しません。
- ブランチ戦略は以下の通りとする。
  - `main`ブランチ：リリース可能な状態を維持する保護ブランチ
  - `develop`ブランチ：各工程のPRをマージする統合ブランチ
  - 工程別フィーチャーブランチ：`feature/<工程名>`の命名規則で作成（例：`feature/requirements`、`feature/mockup`、`feature/design`、`feature/implementation`、`feature/unit-test`、`feature/integration-test`、`feature/system-test`）
- 各工程の作業開始時に、`develop`ブランチから対応する`feature/<工程名>`ブランチを作成して。
- 各工程の作業終了時に、`develop`ブランチへマージして。
- 各工程の成果物（mdファイル・コード等）は必ずフィーチャーブランチにコミットして。
- レビューが完了したら、`feature/<工程名>`ブランチから`develop`ブランチへのPRを`gh pr create`で作成して。
- PRの説明には、工程名・主な成果物・レビュー結果サマリを記載して。
- PRのマージは`gh pr merge --squash`で行い、フィーチャーブランチは削除して。
- 全工程完了後、`develop`から`main`へのPRを作成してマージして。
- git worktreeを活用して、複数のサブエージェントが並行して異なるブランチで作業できるようにして。
  - worktreeの作成：`git worktree add <path> <branch>`
  - worktreeの削除：`git worktree remove <path>`
  - レビューエージェントは専用のworktreeで独立して作業して。

## プロダクト最終品質チェック
- システムテストまで完了した後、スキル「/sonar-scan」を実行した後、スキル「/sonar-report」を実行して、レポートを確認して。
- sonar-reportの全ての指摘について、コードを修正し、デグレが発生していないか、回帰テストを実施して。
