# モック作成工程 rules

## 工程開始チェック
- 要件定義書が存在しない場合、作業を中断して。

## モック作成工程（要件定義レビュー完了後・基本設計の前に実施）
- **事前にモックファイルが提示されている場合は、このモック作成工程をスキップし、提示されたモックを承認済みモックとして基本設計工程に進んで。**
- 要件定義とそのレビューが完了したら、基本設計に進む前に、全画面のモック（HTMLモックアップ）を**3種類（パターンA・B・C）**作成して。
- 各パターンはナビゲーション構造・画面遷移・ダッシュボードの有無が異なる構造的バリエーションとし、配色トーンも各パターンで変えて。
- 全パターン共通：ヒアリングシートの要件「明るめの配色」「子供から高齢者まで使いやすい」に従い、ライト基調の配色とし、十分なコントラスト比（WCAG 2.1 AA基準：4.5:1以上）を確保すること。
- **パターンA：ダッシュボード集約型 ＋ レスポンシブサイドバーナビ**
  - ログイン後にダッシュボードを表示（主要な状態・通知・直近の操作履歴等を一覧集約）
  - 左サイドバーはレスポンシブ対応：PCでは展開状態（アイコン＋ラベル表示）、タブレットではアイコンのみのレール（ミニサイドバー）に縮小、スマホではハンバーガーメニューによるドロワー表示に切り替わる
  - 権限に応じてサイドバーに管理メニューが追加される
  - 配色はライトブルー〜ホワイト基調のクリーンなプロフェッショナルトーン（Salesforce・GitHub・Jira等の業務系メジャーデザインを参考）
  - 情報を俯瞰しやすく、業務的に使いやすい構造
- **パターンB：ドロワーメニュー型 ＋ Material Designインスパイア（ライト基調クリーン）**
  - ログイン後はアクティビティフィード画面に遷移（最新の貸出・返却・予約操作をタイムライン表示）
  - メインナビゲーションはドロワーメニュー方式：上部ヘッダーのハンバーガーアイコンをタップ／クリックすると左側からスライドインしてオーバーレイ表示される
  - PCでは画面幅が広い場合にドロワーを「固定モード（ピン留め）」に切り替え可能とし、常時表示のサイドナビとしても使えるようにする（Material Designのナビゲーションドロワーに準拠）
  - 上部ヘッダーにハンバーガーアイコン・タイトル・検索アイコン・通知アイコン・アバターを配置
  - ホワイト〜ライトグレー基調にブランドカラー（例：ティール・インディゴ系）をアクセントとして使用
  - カード型UIで情報をグループ化し、シャドウと余白で階層を表現（フラットデザイン＋エレベーション）
  - 通知・ステータスはスナックバー（下部）＆バッジで非侵入的に表示
  - Google Workspace・Android標準アプリに近い馴染みやすい操作感
- **パターンC：タイルホーム型 ＋ カード＆タイルナビ ＋ 補助ナビゲーション付き**
  - ログイン後にカードタイル形式のホーム画面（主要機能ごとの大きなタイルを配置）
  - ポータルサイト的な構造で、目的の機能にタイルから直接遷移
  - 上部にシンプルなヘッダー（ホームボタン・ユーザー名・ログアウト）を常時表示し、どの画面からでもホームに戻れる
  - 各機能画面内にはパンくずリスト（ホーム > 図書一覧 > 図書詳細 等）と「戻る」ボタンを配置し、深い階層でも迷わず操作できるようにする
  - スマホでは画面下部にボトムナビゲーションバー（よく使う機能へのショートカット：ホーム・図書検索・貸出状況・プロフィール）を配置
  - 配色は明るいパステル系（例：ライトオレンジ〜イエロー系）で親しみやすさを演出（Microsoft 365ホーム・教育系ポータルを参考）
  - ITに不慣れなユーザーでも「何ができるか」を一目で把握できる直感的な構造
- モックは要件定義で定義した全画面を網羅して。
- モックはブラウザで直接確認できる静的HTML+CSSファイルとして作成して。
  - バックエンドAPIへの通信・データの動的取得は不要。
  - ただし、ドロワー開閉・モーダル表示・タブ切替など、画面の動作確認に必要なUI補助的なJavaScriptは実装して。これらを省略するとモックが正しく動作せず確認できないため。
- レスポンシブ対応（PC・タブレット・スマホ）のレイアウトが確認できるようにして。
- ヒアリングシートのUI/UX要件（配色、文字サイズ、ターゲットユーザー層への配慮等）を反映して。
- モック作成はフィーチャーブランチ `feature/mockup` で作業し、`docs/mockup/` ディレクトリに以下の構成で格納して。
  - `docs/mockup/pattern-a/` — パターンA（全画面）
  - `docs/mockup/pattern-b/` — パターンB（全画面）
  - `docs/mockup/pattern-c/` — パターンC（全画面）
  - `docs/mockup/README.md` — 各パターンの特徴・コンセプト説明
- モック作成完了後、`feature/mockup` から `develop` へのPRを作成して。
- **PRを作成したら、ここで作業を停止し、人間にモックの確認を依頼して。** 人間がモックを確認し、採用パターンの選定やデザイン修正の指示を行います。
- 人間からの修正指示があれば、モックを修正して再度確認を依頼して。
- **人間がモックを承認するまで、基本設計以降の工程に進んではいけません。**
- 人間が承認したモックのデザイン方針を、基本設計以降の画面設計・フロントエンド実装に反映して。

## レビュー方針
- レビュー指摘は後で人間が確認するので、記録として残して。
- レビューの結果で品質がOKになるまで、次の工程を実行しないで。
- レビューでは別の新たなサブエージェントを使い、役割を分担してレビューして。
- レビューエージェントはgit worktreeで独立した作業ディレクトリを使用して。
- レビュー指摘が誤っていないか、指摘対象のコードを確認して、ファクトチェックして。
- レビュー指摘が重複していたら取り除いて。
- レビュー指摘が誤っていたら、指摘を取り下げて。
- レビュー指摘を修正したら、次の工程に進まないで、再レビューを実施し、修正すべき指摘がなくなるまで、レビューを繰り返して。
- 再レビューでは別の新たなサブエージェントを使い、レビューの役割を分担して。
- 重要な指摘だけでなく、必ず軽微な指摘でも処置して。
- レビュー結果はPRのdescriptionに以下の形式で記載して。mdファイルへの別途記録は不要です。
  ```
  ## レビュー結果
  | 指摘番号 | 重要度 | 指摘内容 | 対応結果 |
  |---------|--------|---------|---------|
  | R-001   | 重要   | ...     | 修正済み |
  ```
- レビュー完了後、フィーチャーブランチからPRを作成して。

## GitHubワークフロー方針
- issueは使用しません。
- ブランチ戦略は以下の通りとする。
  - `main`ブランチ：リリース可能な状態を維持する保護ブランチ
  - `develop`ブランチ：各工程のPRをマージする統合ブランチ
  - 工程別フィーチャーブランチ：`feature/<工程名>`の命名規則で作成（例：`feature/requirements`、`feature/mockup`、`feature/basic-design`、`feature/detailed-design`、`feature/implementation`、`feature/unit-test`、`feature/integration-test`、`feature/system-test`）
- 各工程の作業開始時に、`develop`ブランチから対応する`feature/<工程名>`ブランチを作成して。
- 各工程の作業終了時に、`develop`ブランチへマージして。
- 各工程の成果物（mdファイル・コード等）は必ずフィーチャーブランチにコミットして。
- レビューが完了したら、`feature/<工程名>`ブランチから`develop`ブランチへのPRを`gh pr create`で作成して。
- PRの説明には、工程名・主な成果物・レビュー結果サマリを記載して。
- PRのマージは`gh pr merge --squash`で行い、フィーチャーブランチは削除して。
- 全工程完了後、`develop`から`main`へのPRを作成してマージして。
- git worktreeを活用して、複数のサブエージェントが並行して異なるブランチで作業できるようにして。
  - worktreeの作成：`git worktree add <path> <branch>`
  - worktreeの削除：`git worktree remove <path>`
  - レビューエージェントは専用のworktreeで独立して作業して。
