# システムテスト工程 rules

## システムテスト（E2E）
- **テスト仕様書（`docs/test-spec/system/system-test-spec.md`）を必ず作成してから、テストコードの実装を開始して。テスト仕様書にテスト成績（合否・実施結果）の記載は不要。**
- **テストコードの配置先**：E2Eテストコード（Playwright）は `src/e2e/` フォルダに配置して。
- システムテストではE2EテストにPlaywrightを使用し、要件定義を満たしているか検査します。
- Playwrightの設定はscreenshotを「on」（常時キャプチャ）にし、playwright-reportを出力して。
- E2Eテストでは、テスト結果だけでなく、エビデンスの画面イメージも記録して。
- E2EテストはすべてのFR-IDをカバーして。未カバーの機能要件がある場合はレビューNGとする。
- E2Eテストではモックの画面のレイアウト・ラベル・ボタン名・ナビゲーション構造が忠実に反映されているか、画面イメージを比較し、差異がある場合はレビューNGとする。
- E2Eテストのアサーションは必ず具体的な条件を検証して。以下のような形式的アサーションは禁止します。
  - `expect(pageText).toBeTruthy()` のみ（テキストの具体的な内容を検証すること）
  - `expect(page.locator('body')).toBeVisible()` のみ（より具体的な要素・テキスト・URLを検証すること）
  - `expect(hasError || !page.url().includes('...'))` のような後半条件が常に真になる複合条件
  - `expect([200, 400]).toContain(status)` のような成功・失敗どちらでも通過するステータスコード範囲チェック（成功を期待するなら `expect(status).toBe(200)` のように具体値で検証すること）
  - `expect(condA || condB).toBe(true)` のようなOR条件アサーション（どちらの状態なのかを特定して、片方の具体的な条件のみで検証すること）
  - `expect(page).toHaveURL(/pattern1|pattern2/)` のような複数URL許容パターン（遷移先URLを1つに特定して検証すること）
  - `if (await element.isVisible())` でテスト本体をスキップする条件分岐（要素が表示されることを前提条件として保証した上でテストすること）
- 操作失敗時のフォールバックパスにも、失敗状態を示す具体的なアサーションを実装して。
- 貸出上限チェック（FR-014相当）や期限超過ユーザの貸出制限（FR-015相当）等の業務ルールは、エラーメッセージの具体的な文言を `toHaveText()` や `toContainText()` で検証して。
- 未認証ユーザが認証必須ページへアクセスした際のリダイレクト、および通常ユーザが管理者専用URLへアクセスした際のアクセス拒否をE2Eでテストして。
- 操作ログに関する機能要件のE2Eテストでは、操作実行後にログファイルまたはログ出力を検証し、操作者ID・操作種別・対象リソースIDがログに記録されていることをアサーションで確認して。「ログが出力されていること」だけでなく、ログの具体的な内容を検証すること。
- **テストコード作成時は、テスト仕様書だけでなく、関連する実装済みのソースコード（`src/backend/src/main/`・`src/frontend/src/`）を必ず読み込んで参照すること。**
- 実装コードのクラス構造・メソッドシグネチャ・分岐条件・例外処理・依存関係を把握した上でテストを作成して。仕様書のみに基づく推測でテストを書くことを禁止する。

## 複雑な運用シナリオのE2Eテスト（必須）
- 単一機能の動作確認にとどまらず、**実際の業務運用を想定した複数機能・複数ロール・複数状態が絡み合うシナリオ**を可能な限り多く作成して。シナリオが少ない場合はレビューNGとする。
- 以下のカテゴリに沿って、システムの機能要件から導出できる運用シナリオをすべて洗い出してテスト化すること：

  ### 複数ロール連携シナリオ
  - 異なるロール（一般ユーザ・管理者等）が同一リソースに対して順序付きで操作するシナリオ（例：一般ユーザが申請→管理者が承認→一般ユーザが結果確認）
  - ロール切り替え（別ブラウザコンテキストまたは別ページを使用）によって、各ロールの画面・操作権限の差異を同一テスト内で検証するシナリオ

  ### ステータス遷移シナリオ
  - リソースのステータスが複数段階を経て最終状態に至るまでの一連の遷移を、途中の中間状態もアサーションしながら通しで検証するシナリオ
  - 正常遷移だけでなく、遷移不可条件（業務ルール違反・権限不足・上限超過等）で意図的に遷移をブロックし、エラー状態と回復操作までを含むシナリオ

  ### 上限・制約・競合シナリオ
  - 上限値（件数・数量・期日等）ちょうどに到達させてから次の操作を行い、制限発動と解除の両方を検証するシナリオ
  - 同一リソースへの連続操作（登録→更新→削除→再登録等）を一連の流れで実施し、各操作後の状態を検証するシナリオ
  - 期限切れ・失効・無効化の状態を意図的に作り出し、その状態での操作拒否と管理者による回復を検証するシナリオ

  ### 長期・複合業務フローシナリオ
  - 複数の機能を連続して使用する長いフロー（複数画面をまたぐ一連の業務手順）を1テストとして実装するシナリオ（画面間でデータが引き継がれることを含めて検証）
  - 中断・再開を含む業務フロー（途中でログアウト→再ログイン後に作業継続）のシナリオ
  - 複数のリソースを同時に操作・管理する一括処理や繰り返し操作のシナリオ

  ### データ整合性シナリオ
  - 一方のロールによる変更が、他のロールの画面に即時反映されることを検証するシナリオ
  - 一連の操作後に、関連する複数の画面・一覧・詳細・ログのすべてが整合した状態になっていることをまとめて検証するシナリオ

- 各複合シナリオは独立したテストファイルまたはdescribeブロックとして実装し、シナリオ名にはストーリー性のある日本語名称を付けて（例：`管理者が承認→上限到達→ユーザが追加申請を拒否される流れ`）。
- テスト仕様書（`docs/test-spec/system/system-test-spec.md`）に各シナリオの前提条件・操作ステップ・検証ポイントを記載して、テスト意図が明確になるようにすること。

## テスト仕様書の作成（必須）
- 単体テスト・結合テスト・システムテスト（E2E）のすべてのテスト工程で、**テストコード実装前に**最低限のテスト仕様書をmdファイルとして作成して。テスト仕様書が存在しない状態でテストコードを実装することを禁止します。
- テスト仕様書に**テスト成績（テスト実施結果・合否記録）の記載は不要**。仕様書はテストの設計情報のみを記載する。
- テスト仕様書・テストコードの保存先と対応工程：
  - システムテスト：仕様書 `docs/test-spec/system/system-test-spec.md`、テストコード `src/e2e/`（`feature/system-test`ブランチ）
- 各テスト仕様書には以下の項目を最低限含めて：
  - テスト対象の機能・クラス・エンドポイント
  - テストケースID（TC-xxx）と対応するFR-ID
  - テスト条件（前提条件・入力データ）
  - 期待結果（具体的な検証項目）
  - テスト種別（正常系/異常系/境界値）
- テスト仕様書は各テスト工程のフィーチャーブランチにコミットし、PRの成果物として含めて。テスト仕様書が含まれていないPRはレビューNGとする。

## レビュー方針
- レビュー指摘は後で人間が確認するので、記録として残して。
- レビューの結果で品質がOKになるまで、次の工程を実行しないで。
- レビューでは別の新たなサブエージェントを使い、役割を分担してレビューして。
- レビューエージェントはgit worktreeで独立した作業ディレクトリを使用して。
- レビュー指摘が誤っていないか、指摘対象のコードを確認して、ファクトチェックして。
- レビュー指摘が重複していたら取り除いて。
- レビュー指摘が誤っていたら、指摘を取り下げて。
- レビュー指摘を修正したら、次の工程に進まないで、再レビューを実施し、修正すべき指摘がなくなるまで、レビューを繰り返して。
- 再レビューでは別の新たなサブエージェントを使い、レビューの役割を分担して。
- 重要な指摘だけでなく、必ず軽微な指摘でも処置して。
- レビュー結果はPRのdescriptionに以下の形式で記載して。mdファイルへの別途記録は不要です。
  ```
  ## レビュー結果
  | 指摘番号 | 重要度 | 指摘内容 | 対応結果 |
  |---------|--------|---------|---------|
  | R-001   | 重要   | ...     | 修正済み |
  ```
- レビュー完了後、フィーチャーブランチからPRを作成して。

## 完了前必須チェックリスト（システムテスト工程）

### テスト仕様書・テストコードの確認
- `docs/test-spec/system/system-test-spec.md` が存在すること
- テスト仕様書にテスト対象・TC-ID・FR-ID・テスト条件・期待結果・テスト種別が記載されていること
- E2Eテストコード（Playwright）が `src/e2e/` フォルダに存在すること
- **テスト仕様書が存在しない場合、システムテストレビューはNG**
- **テストコード作成時は、テスト仕様書だけでなく、関連する実装済みのソースコード（`src/backend/src/main/`・`src/frontend/src/`）を必ず読み込んで参照すること。**
- 実装コードのクラス構造・メソッドシグネチャ・分岐条件・例外処理・依存関係を把握した上でテストを作成して。仕様書のみに基づく推測でテストを書くことを禁止する。

### E2Eテストカバレッジの確認
- 要件定義書の全FR-IDに対応するE2Eテストが存在すること（未カバーFRを明示的にリストアップして確認）
- **未カバーFRが1件でもある場合、テストレビューはNG**

### E2Eテストアサーションの確認
以下のパターンが存在しないことを検索して確認して：
```bash
grep -rn "toBeTruthy()\|toBeVisible.*body\|hasError ||\|toContain(status)\|\[200.*400\]\||| .*toBe(true)\|condA || condB\|toHaveURL.*|.*|\|if.*isVisible" src/e2e/ --include="*.ts" --include="*.js" 2>/dev/null || grep -rn "toBeTruthy()\|toBeVisible.*body\|\[200.*400\]\||| .*\.toBe(true)" tests/ --include="*.ts"
```
禁止パターン：
- `expect(pageText).toBeTruthy()` のみのアサーション
- `expect(page.locator('body')).toBeVisible()` のみのアサーション
- 後半条件が常に真になる複合条件（例：`expect(hasError || !page.url().includes('/books'))`)
- `expect([200, 400]).toContain(status)` 等の成功・失敗いずれでも通過するステータスコードチェック
- `expect(condA || condB).toBe(true)` 等のOR条件で複数状態のいずれでも通過するアサーション
- `expect(page).toHaveURL(/url1|url2/)` 等の複数URL許容パターン
- `if (await element.isVisible())` でテスト本体をスキップする条件分岐
- フォールバックパスに形式的アサーションのみ
- **禁止パターンが1件でも発見された場合、テストレビューはNG（修正後に再検索して確認すること）**

### 権限制御E2Eテストの確認
- 未認証ユーザが認証必須ページにアクセスしたときのリダイレクトテストが存在すること
- 通常ユーザが管理者専用URL（`/admin/**`等）にアクセスしたときのアクセス拒否テストが存在すること
- **未実装の場合、テストレビューはNG**

## GitHubワークフロー方針
- issueは使用しません。
- ブランチ戦略は以下の通りとする。
  - `main`ブランチ：リリース可能な状態を維持する保護ブランチ
  - `develop`ブランチ：各工程のPRをマージする統合ブランチ
  - 工程別フィーチャーブランチ：`feature/<工程名>`の命名規則で作成（例：`feature/requirements`、`feature/mockup`、`feature/basic-design`、`feature/detailed-design`、`feature/implementation`、`feature/unit-test`、`feature/integration-test`、`feature/system-test`）
- 各工程の作業開始時に、`develop`ブランチから対応する`feature/<工程名>`ブランチを作成して。
- 各工程の作業終了時に、`develop`ブランチへマージして。
- 各工程の成果物（mdファイル・コード等）は必ずフィーチャーブランチにコミットして。
- レビューが完了したら、`feature/<工程名>`ブランチから`develop`ブランチへのPRを`gh pr create`で作成して。
- PRの説明には、工程名・主な成果物・レビュー結果サマリを記載して。
- PRのマージは`gh pr merge --squash`で行い、フィーチャーブランチは削除して。
- 全工程完了後、`develop`から`main`へのPRを作成してマージして。
- git worktreeを活用して、複数のサブエージェントが並行して異なるブランチで作業できるようにして。
  - worktreeの作成：`git worktree add <path> <branch>`
  - worktreeの削除：`git worktree remove <path>`
  - レビューエージェントは専用のworktreeで独立して作業して。

## プロダクト最終品質チェック
- システムテストまで完了した後、実装後、スキル「/sonar-scan」を実行した後、スキル「/sonar-report」を実行して、レポートを確認して。
- sonar-reportの全ての指摘について、コードを修正し、デグレが発生していないか、回帰テストを実施して。
