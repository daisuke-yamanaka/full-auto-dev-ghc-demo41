単体テスト（仕様書・テストコード）に対して強化レビューを実施してください。

## 強化レビューの実施手順

**3つの独立したレビューエージェント**を git worktree で並行起動し、それぞれ異なる視点でレビューを実施してください。

### エージェント1：テスト仕様書チェック

- `docs/test-spec/unit/` にテスト仕様書が存在するか
- 全テストケースに TC-ID・FR-ID・テスト条件・期待結果・テスト種別が記載されているか
- 以下の観点でテストケースが網羅されているか
  - 境界値分析（上限値・下限値・その前後）
  - 同値分析（代表値での正常系）
  - 異常系（入力誤り・権限不足・リソース未存在・競合・上限超過等）
  - ビジネスルール（要件定義書の各 FR の受け入れ条件）
- 要件定義書の全 FR-ID に対応するテストケースが存在するか（漏れがないか）

### エージェント2：バックエンドテスト品質チェック

- 全 DAO/Repository インターフェースにテストクラスが存在するか
- DB アクセスを含むテストが実 DB（H2 インメモリ等）を使用しているか（モックで代替していないか）
- GlobalExceptionHandler のテストが存在するか（各例外クラス → 期待 HTTP ステータスコードの検証）
- 以下のコマンドで形式的アサーションの存在を確認する：
  ```bash
  grep -rn "verify.*any(.*\.class)" src/backend/src/test/java/ --include="*.java"
  grep -rn "ArgumentCaptor\|argThat" src/backend/src/test/java/ --include="*.java"
  grep -rn "@Transactional" src/backend/src/test/java/ --include="*.java"
  ```
- `verify(mock).method(any(Entity.class))` のみで、引数の具体値を検証していない形式的アサーションがないか
- 楽観的ロック（バージョン不一致時の競合エラー）のテストケースが存在するか
- 操作ログの出力内容（操作者 ID・対象リソース ID を含むか）を検証するテストが存在するか

### エージェント3：フロントエンドテスト・カバレッジチェック

- 全ページコンポーネントにテストファイルが存在するか
- カスタムフックに `renderHook` を使ったテストがあるか
- テストカバレッジが90%以上か
  ```bash
  cd src/frontend && npx jest --coverage --coverageReporters=text-summary 2>/dev/null | tail -5
  ```
- `getByTestId` の多用がなく、アクセシビリティベースのクエリ（`getByRole` 等）を優先しているか
- 画面状態遷移表の各状態（ローディング・データあり・データなし・エラー等）に対応するテストケースが存在するか
- ユーザー操作（ボタンクリック・フォーム入力）後の状態変化を検証しているか

## 集約・修正フロー

1. 3エージェントの指摘を集約し、重複・誤りを除去する
2. 全指摘を修正する（軽微な指摘も必ず対処する）
3. 修正後、さらに**新たな2エージェント**で再レビューを実施する
4. 指摘がなくなるまで繰り返す
5. 最終的なレビュー結果をPRのdescriptionに記載する
