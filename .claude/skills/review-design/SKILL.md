設計書（`docs/design/`）に対して強化レビューを実施してください。

## 強化レビューの実施手順

**3つの独立したレビューエージェント**を git worktree で並行起動し、それぞれ異なる視点でレビューを実施してください。

### エージェント1：画面設計書チェック

`docs/design/screens/SCR*.md` の各画面について以下を確認する：

- **モック整合性**
  - 画面項目定義のラベル・ボタン名・リンク名が承認済みモックと一致しているか
  - モックに存在する全画面が画面設計書で定義されているか
  - 画面遷移図がモックのナビゲーション構造を反映しているか

- **ボタン表示条件表の網羅性**
  - ログインユーザーの状態（未処理・処理中・完了・上限到達等、対象システムの全状態）を行に、画面上の全ボタンを列に取り、「表示（活性）」「表示（非活性）」「非表示」の3値で全組み合わせが定義されているか
  - 状態の組み合わせに漏れがないか（特にユーザーが既に操作中・所有中の状態が定義されているか）

- **アクション定義（A01〜AN）の網羅性**
  - 画面項目定義のボタン（B0N）すべてに対応するアクション（A0N）が定義されているか
  - 「〇〇リンク押下 → SCR00X へ遷移」形式のナビゲーションアクションが A0N として定義されているか
  - 各アクションに対応する API エンドポイントが関連 API 表に記載されているか

- **B・A・API の3層整合**
  - ボタン（B0N）→ アクション（A0N）→ 関連 API の対応関係に漏れがないか

### エージェント2：OpenAPI仕様チェック

- **エンドポイント網羅性**
  - 全 FR-ID に対応するエンドポイントが定義されているか
  - URL 命名がロール・対象リソース・操作意図を明示しているか（認証ユーザー自身は `/api/me/...`、管理者専用は `/api/admin/...` 等）
  - 各エンドポイントに全ステータスコード（200/201/400/401/403/404/409/500）のレスポンスが定義されているか

- **レスポンスフィールドの網羅性（3種類の必須フィールド）**
  1. **楽観的ロック用 `version`**：フロントエンドから更新・削除操作が発生するリソースを含む全レスポンス（一覧・詳細・集約レスポンス等）に定義されているか
  2. **ユーザー状態判定フィールド（`currentUser*` 等）**：画面状態遷移表の各状態を判定するために必要なフィールドが、対応するレスポンスに定義されているか
  3. **ナビゲーション用 ID**：一覧・集約画面のレスポンスで詳細へ遷移する要素があれば、遷移先リソース ID が含まれているか

- **排他制御設計**
  - 楽観的ロック対象テーブルすべてにバージョン管理カラムが定義されているか

### エージェント3：要件充足・整合性チェック

- トレーサビリティマトリクスの全エンドポイントが openapi.yaml に含まれているか
- openapi.yaml に定義された全エンドポイントが画面設計書のアクション定義（A0N）と対応しているか
- ER 図・テーブル定義が機能要件を充足しているか
- 用語が全設計ドキュメントで統一されているか（要件定義書の用語集と一致しているか）
- ドキュメント間の矛盾がないか（権限・フロー・データ構造）

## 集約・修正フロー

1. 3エージェントの指摘を集約し、重複・誤りを除去する
2. 全指摘を修正する（軽微な指摘も必ず対処する）
3. 修正後、さらに**新たな2エージェント**で再レビューを実施する
4. 指摘がなくなるまで繰り返す
5. 最終的なレビュー結果を設計のPRのdescriptionに記載する
