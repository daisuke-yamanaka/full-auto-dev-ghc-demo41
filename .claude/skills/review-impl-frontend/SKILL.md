フロントエンド実装コード（`src/frontend/`）に対して強化レビューを実施してください。

## 強化レビューの実施手順

**3つの独立したレビューエージェント**を git worktree で並行起動し、それぞれ異なる視点でレビューを実施してください。

### エージェント1：画面設計書アクション定義の網羅チェック

`docs/design/screens/SCR*.md` の各画面について以下を1件ずつ突合する：

- **全アクション定義（A01〜AN）の実装確認**
  - 各画面のアクション定義（SCR00X-A01〜A0N）に対応する実装がすべて存在するか
  - 特に「〇〇リンク押下 → SCR00X へ遷移」形式のナビゲーションアクションが実装されているか
  - 未実装のアクションが1件でも存在する場合はNG

- **画面状態遷移表の全状態の実装確認**
  - ボタン表示条件表に定義された全状態（ユーザーの処理状態に基づく分岐）が実装されているか
  - 各状態でのボタン表示・非表示・非活性が設計書と一致しているか

- **同一 UI パターンの横展開確認**
  - 「リソース名クリックで詳細へ遷移」「ステータス変更ボタン」など、同じ UI パターンが複数画面に存在する場合、全画面に実装されているか

- 以下のコマンドでテストファイルの存在を確認する：
  ```bash
  find src/frontend/src -name "*.test.tsx" -o -name "*.test.ts" -o -name "*.spec.tsx" -o -name "*.spec.ts" 2>/dev/null | sort
  ```

### エージェント2：テスト品質チェック

- 全ページコンポーネントにテストファイルが存在するか
- API 通信テストで axios がモック化されているか
  ```bash
  grep -rn "jest.mock.*axios\|axios.*mock" src/frontend/src/ --include="*.test.*" --include="*.spec.*" 2>/dev/null
  ```
- `getByTestId` を多用していないか（`getByRole`・`getByLabelText`・`getByText` 等のアクセシビリティベースのクエリを優先しているか）
  ```bash
  grep -rn "getByTestId" src/frontend/src/ --include="*.test.*" --include="*.spec.*" 2>/dev/null
  ```
- テストカバレッジが90%以上か
- カスタムフックに `renderHook` を使ったテストがあるか

### エージェント3：コード品質・整合性チェック

- **OpenAPI 整合性**：全 API 呼び出し（URL・HTTP メソッド・リクエスト/レスポンスの型定義）が `docs/design/openapi.yaml` と一致しているか
- **DRY 原則**：同一 UI ロジック・API 呼び出しが3箇所以上に重複していないか
- **定数管理**：マジックナンバーがない（ビジネスルールの数値が定数として定義されているか）
- **グローバル例外ハンドリング**：API エラーの処理が共通化されているか

### エージェント4：承認済みモックとのデザイン整合チェック

画面設計書（SCR*.md）に記載された「承認済みモックとの対応」セクションを参照し、承認済みモック HTML（`docs/mockup/採用パターン/`）と実装を1画面ずつ突合する：

- **ナビゲーション構造**：採用パターンのナビゲーション構造（サイドバー・アイコンナビ・タイルホーム等）が実装に再現されているか
  - パターンA採用なら：左サイドバー＋ダッシュボードが実装されているか
  - パターンB採用なら：左端アイコンナビ＋グラスモーフィズム＋グローバル検索バーが実装されているか
  - パターンC採用なら：カードタイル形式のホーム画面が実装されているか

- **配色**：モックで使用した背景色・プライマリカラー・アクセントカラーが実装と一致しているか
  - CSS 変数または定数として定義されており、モックの色値（HEX・RGB 等）と一致しているか
  - 著しく異なる配色が使われていないか

- **コンポーネントスタイル**：以下の要素がモックと視覚的に一致しているか
  - カード・パネルの角丸・シャドウ・余白
  - ボタンのスタイル（形状・色・ホバー状態）
  - テーブル・リストのレイアウト
  - フォーム入力欄のスタイル

- **空状態・エラー状態**：モックに定義された空状態メッセージ・エラーメッセージの文言とレイアウトが実装と一致しているか

- **ラベル・ボタン名**：画面上のラベル・ボタン名・見出し文言がモックと一致しているか

- **上記のいずれかが著しく異なる場合、実装レビューはNG**

## 集約・修正フロー

1. 3エージェントの指摘を集約し、重複・誤りを除去する
2. 全指摘を修正する（軽微な指摘も必ず対処する）
3. 修正後、さらに**新たな2エージェント**で再レビューを実施する
4. 指摘がなくなるまで繰り返す
5. 最終的なレビュー結果をPRのdescriptionに記載する
